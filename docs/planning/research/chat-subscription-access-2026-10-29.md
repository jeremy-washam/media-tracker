# Independent subscription and architecture audit

Public research checked 2026-10-29 (America/New_York). No sign-in, credential inspection, account changes, paid activation, deployment, or repository edits performed. Official pages were opened, not just search snippets. Repository product/architecture/standards/implementation/ADR-index/long-term-vision documents were read; installed manifests do not list Agents, AIChatAgent, Think, or AI SDK. Recommendations below are design judgments, not implementation results.

## Decisive recommendation

**If the owner has an eligible paid Pro subscription, use the existing private hosted React/Hono application, Cloudflare AIChatAgent for chat transport/lifecycle, and ordinary Responses API requests funded exclusively by the subscription's included API credits.** This satisfies the stated requirement of personal-subscription funding without a separate API payment, subject to verifying the owner's benefit and removing paid funding paths. It does require an API organization, project, server-side API key, and one-time benefit claim. It does not use shared ChatGPT/Codex quota.

Do not make SIWC a prerequisite for this hosted version, do not add Codex App Server, and do not choose Think merely to avoid writing a small bounded model/tool loop. Keep the provider and tool interfaces owned by Imladris. If the account is Plus, or the Pro benefit cannot be claimed, choose an entirely local personal SIWC runtime as the supported no-extra-inference-payment fallback; ordinary private hosted SIWC requires selection/approval.

## Subscription-funded API credits: confirmed facts

The [API credit guide](https://developers.openai.com/api/docs/guides/chatgpt-api-credits) documents:

- Pro $100/$200/$500 tiers receive $100/$200/$500 per billing cycle. Business Standard/Premium receive $20/$100 per paid seat, pooled with a $500 monthly workspace cap; annual Business grants have annual handling.
- Eligibility: paid active subscription at least seven days old; subscription/workspace ownership and receiving API-organization ownership; matching account email. Trial/complimentary plans do not qualify. Plus is ineligible.
- One-time linking/claim; automatic renewal grants while eligible; initial grant prorated; unused Pro credits expire at subscription-cycle end, without rollover.
- No API payment method required. Linked-organization project API keys use the benefit.
- Responses, built-in web search, file search, Code Interpreter and associated storage/tool costs are covered. Codex via API keys is excluded; ChatGPT/signed-in Codex limits do not increase.
- Free credits are consumed first, then purchased credits if any. With no credits left, requests fail `429 credit_balance_exhausted`.

The [API changelog](https://developers.openai.com/api/docs/changelog) dates this benefit to October 28, 2026. Thus blanket older statements that a ChatGPT subscription never includes API use are now stale. The benefit is a finite dollar allowance, not unlimited API use or an automatic transfer of shared ChatGPT quota.

The [pricing page](https://developers.openai.com/api/docs/pricing) prices ordinary web search at $10/1,000 calls plus search-content tokens at model rates. Those are metered costs against the included API balance; an external search-provider subscription is unnecessary for OpenAI web search. Search remains an explicit capability, not something to enable on every library-only question. The [web-search guide](https://developers.openai.com/api/docs/guides/tools-web-search) requires visible clickable inline citations when displaying web-derived information.

### No-additional-payment controls

Use a receiving organization with **no payment method, no purchased balance, and Auto Recharge disabled**. Verify the actual billing arrangement instead of assuming that a new project isolates the organization's funding. There is no documented per-request “included subscription credits only” switch. Never implement paid-provider, paid-key, or account fallback.

The [spend-limit guide](https://developers.openai.com/api/docs/guides/spend-limits) now provides enforceable organization and project monthly hard limits; older advice that all budgets are alerts is outdated. Alerts alone do not stop traffic. Hard enforcement can lag slightly, allowing recorded usage to exceed the configured amount. Therefore use hard limits as secondary safeguards, not proof of an exact zero-overage guarantee on a payment-enabled organization. The documented credit-only/no-payment balance-failure path is the stronger funding boundary. Calendar spend limits and subscription-cycle credit expiry are different concepts and must both be displayed/handled accurately.

Add an application admission budget with conservative per-turn reservations, bounded context/output/steps/search calls, one active turn per chat, and no automatic continuation after interruption. Stop on billing errors and show exhausted/expired entitlement without suggesting that the library itself is unavailable. The docs establish the intended stop behavior; this audit did not inspect whether the owner's actual organization has other funding or contractual billing.

## SIWC eligibility: resolve the apparent contradiction

The [quickstart](https://developers.openai.com/siwc/quickstart) separates identity from permission to spend ChatGPT plan allowance. Eligible Plus/Pro users can grant plan usage; private clients are selected, and commercial identity integration is a limited trial. Identity scopes alone do not fund inference or grant conversation access.

The [official integration cookbook](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt) explicitly includes personal projects running locally alongside open-source projects and selected private apps. It directs paid or remotely hosted apps to request access before offering them. Hence **private local personal does not require publishing the whole application as open source**; private hosted does not become eligible merely because it has one user.

The [overview](https://developers.openai.com/siwc/token-sharing-open-source) asks paid/remotely hosted apps to submit interest, but also describes distinct laptop and self-hosted-VM hosts sharing a user/workspace client. The more specific [self-hosted-VM guide](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms) explicitly applies to an **open-source app** on a remote VM: do OAuth locally, securely transfer that registration, retain a distinct VM host ID, and let the VM own later refreshes. Transferred-session host-specific usage attribution and revocation are unavailable.

**Resolution:** the documented OSS self-hosted VM is a narrow supported case, not permission for arbitrary private remotely hosted services. A private Cloudflare Worker is not automatically that case. Nor does this documentation prove that a hosted frontend with a local SIWC proxy qualifies; use a clearly local personal application or obtain approval rather than building around that ambiguity. Publishing a standalone bridge while the actual product remains a private hosted service also needs clarification, not an assumption.

The [user guide](https://learn.chatgpt.com/docs/sign-in-with-chatgpt) says app usage counts against existing plan allowance and apps can receive weekly percentage caps. The [session guide](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions) additionally says Plus has a shared five-hour limit across apps, whereas that five-hour limit does not apply to Pro. Neither statement grants unlimited usage. The same guide requires protected runtime token storage and serialized rotating-token refresh; tokens must stay out of browser storage/logs.

The [recovery guide](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery) states plan-usage errors stop inference and OpenAI does not silently switch billing paths. Missing `chatgpt.tokens.use.direct` means identity may remain connected but inference must stay disabled. Distinguish ineligible, app/plan limit, unsupported capability, route, temporary availability, and invalid-session errors. Consent retry parameters themselves have rollout caveats (`force_reconsent` only after deployment confirmation); do not force consent on ordinary reconnects.

## SIWC models, tools, and Codex

The [models guide](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference) requires account-specific `GET /v1/models`, then public `POST /v1/responses` with the OAuth bearer token. Preserve account ordering/display names/slugs and refresh after account switching. Do not use ChatGPT backend-api endpoints. Completion requires `response.completed`, not a login badge, catalog entry, first streamed text, or a merely closed stream; usage failure can arrive after streaming begins.

The [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) require `store:false`, `stream:true`, explicit history arrays, no HTTP `previous_response_id`, and numerous omitted ordinary Responses fields. Namespaced function/custom tools or additional-tools input items support application-executed library queries. Web search depends on selected model and account/workspace policy. Hosted MCP/connectors, file search, tool search, Code Interpreter, image generation and native computer use are unsupported. Text/images/files depend on model support; audio/video and file-upload/transcription APIs are excluded. Therefore existing article text/transcripts can be passed as text, but SIWC does not supply a hosted corpus-search or transcription pipeline. Client-side tool execution does not rescue unsupported `tool_search`.

The [SIWC app-server guide](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) does document supplying an app-owned SIWC access token to a Codex child process using a Responses provider. A bundled `model/list` catalog is not entitlement proof; a completed inference turn is. The application owns refresh and must restart/reinitialize/resume for the env-token configuration. This is different from extracting Codex's own cached login.

The [main App Server reference](https://learn.chatgpt.com/docs/app-server) recommends SIWC migration for local/OSS applications and explicitly prohibits its legacy authentication for commercial or hosted services. It supplies command/file/permission approval requests, streamed events/history, MCP, and experimental dynamic tools. App Server is useful for a coding-style runtime with those powers; a read-only media chat would inherit unnecessary process, permissions, history, auth and tool complexity. It does not grant private-hosted eligibility, universal model entitlements, or free API access. Local MCP execution versus unsupported hosted Responses MCP are different mechanisms, not a contradiction.

## Independent full application design recommendation

Use one chat Durable Object per conversation behind the existing owner-only Hono/Access boundary. The provider-independent core owns turn admission, bounded read-only library tool schemas/execution, evidence references, model capabilities, cost policy, and result status. OpenAI's adapter initially uses ordinary Responses with subscription credits and native web search. Keep credentials in Worker secrets. Future adapters need their own supported funding/authorization checks; provider abstraction does not make another vendor's consumer subscription usable as an API.

Use direct repository/service queries for library tools, not a public MCP server, shell, arbitrary SQL, browser automation, or a second search service. Start with existing bounded lexical/structured retrieval across metadata/history/ratings/reviews/highlights and authorized text. Return stable item/source/occurrence identifiers, date precision, excerpt locations and source-record provenance. A tool may report missing transcripts or unknown consumed dates. Separate public web citations from personal-library evidence. Preserve provider/model, tool arguments/results, retrieved evidence versions and generated-artifact versions. Generated claims never overwrite imported facts.

For history portability, own a versioned export/restore contract for messages, parts, tool results, citations, artifacts and turn statuses; provider raw payloads can be supplemental. Keep durable transcript storage distinct from bounded model context. A future adapter must not be forced to understand OpenAI response IDs to load a chat. Do not drop historical messages merely to fit a context window. Editing/regenerating creates a retained version or branch. D1 can hold conversation indexes/search metadata and the existing repository layer can expose exports; avoid blindly duplicating full transcripts into multiple authoritative stores.

### Harness comparison

The [Think comparison](https://developers.cloudflare.com/agents/harnesses/think/) describes AIChatAgent as a persistence/streaming/abort/resume protocol adapter with an application-owned model call. Think adds an opinionated loop, tree sessions, non-destructive branching/compaction, FTS and model-writable context memory; it remains experimental. AIChatAgent's built-in regeneration is destructive and `maxPersistedMessages` deletes old history. **Recommendation:** AIChatAgent plus owned bounded loop, explicit retained regeneration, and non-destructive context selection. Think is the second choice if conversation-tree/memory features become immediate requirements and its experimental API is accepted. A completely owned Hono/SSE loop maximizes transport freedom but makes Imladris rebuild lifecycle/concurrency/cancellation/recovery; choose it only if the Agents adapter proves materially restrictive in a small spike.

The [chat-agent guide](https://developers.cloudflare.com/agents/agent-class/communication-channels/chat/chat-agents/) distinguishes reconnect replay from eviction recovery. Wire explicit `stop()` and propagate its abort signal through model and tool work; cleanup/disconnect alone ordinarily leaves inference running. Default eviction recovery may spend again by continuing/retrying. For the first version, persist cancellation intent and return `{continue:false}` from recovery, preserving partial output and marking interruption. Let the user retry as a retained new attempt. Pin versions and verify these behaviors against the actually installed release rather than assuming documentation equals tested integration.

## Infrastructure cost boundary

[Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/) makes the paid plan a $5/month minimum with usage overages; per-invocation CPU limits reduce runaway CPU but are not a total monthly dollar cap. [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) includes wall-clock duration while active, request and SQLite storage dimensions; an LLM stream can hold the object active even while waiting on the provider. [D1's FAQ](https://developers.cloudflare.com/d1/reference/faq/) confirms paid-tier excess reads/writes/storage are billed. Free-tier hard stops do not become paid-tier hard stops. OpenAI credits cover none of these Cloudflare charges.

The repository currently records $5/month with $0 additional charges. Therefore a hosted chat launch needs measured usage/headroom plus durable reservations for turns, concurrency, duration, steps/searches and transcript/chunk writes. Reuse existing resources and bound background work. This audit found no documented global Cloudflare paid-account $0-overage switch; do not claim one. Expected low single-user volume is not evidence of an enforced spending ceiling. An all-local runtime is the cleanest fallback if an enforceable no-incremental-cloud-cost requirement cannot be satisfied on the existing deployment.

## Irreducible account and implementation checks

No check below was performed or authorized by this public audit.

1. Owner verifies exact subscription tier, age, ownership and email; sees the included-API-credit benefit. Before activation, review the receiving organization and existing payment/purchased-credit/contract settings. Claiming/linking and creating secrets remain an explicit owner action; this recommendation is not activation approval.
2. After an approved claim, verify actual grant amount, expiry and linked organization; no paid funding, Auto Recharge or payment-enabled fallback. Use a project from that organization. Confirm hard-limit enforcement controls are available and distinguish subscription renewal from monthly cap reset.
3. Complete a minimal request, one real library-tool round trip, and a web-search request with citations using the selected API model. Confirm credit-funded usage in that organization's dashboard. Model catalog or a Pro label cannot prove actual access. Do not drain credits to test exhaustion: inject documented billing errors in tests; inspect provider settings and use the official exhausted-balance behavior.
4. Verify context/output/step/search/turn caps, duplicate-submit dedupe, Stop while a model and a tool are running, refresh/reconnect, deploy/eviction mid-stream, late provider completion, partial history and artifact retention/export/restore. Billing errors must stop rather than trigger retries or another provider.
5. Measure Cloudflare request/duration/SQLite/D1/R2 effects of a representative turn and reconnect. Prove admission budgets against current headroom before hosted activation; keep chat disabled if no safe allowance remains.
6. Only for SIWC fallback: owner completes local OAuth, validates returned identity and plan-use scope, then performs account catalog discovery, a completed text request, namespaced library-tool round trip and web-search request. Verify refresh/restart and disconnect/revocation handling without reading Codex credentials. If remotely hosted private SIWC remains desired, obtain OpenAI acceptance for that exact deployment first. A successful unauthorized technical request is not policy approval.

Remaining uncertainty is narrow: actual owner entitlement/funding, selected model/web-search access, pinned-package interoperability, measured Cloudflare headroom, and any private-hosted SIWC approval. The public sources establish supported routes; they do not establish those account-specific facts.
